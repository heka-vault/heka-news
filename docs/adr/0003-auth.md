# 0003. Auth: GitHub OAuth and invitation links

- Status: accepted (implementation is phase 3; the tables exist now)
- Date: 2026-10-18

## Context

Anyone can read. Only members can post, comment, vote and flag, and membership is by invitation:
the engineers in heka's group, and people they invite. We do not want to run email delivery or
store passwords at launch.

## Decision

- **Sign-in is GitHub OAuth.** A user row stores the GitHub numeric id (stable across renames)
  and the login (shown, and used in URLs as `/u/:login`).
- **Joining needs a one-time invitation link.** A member creates an invite; the link carries a
  random token. Only the token's SHA-256 is stored (`invites.code_hash`). Following the link and
  signing in with GitHub creates the account with `invited_by` set, and marks the invite used.
  Invites can expire and be revoked.
- **The invite tree is public** (`/tree`), as on Lobsters: who invited whom is part of how the
  community holds itself accountable.
- **Sessions live in SQLite** (`sessions`), keyed by the SHA-256 of a random token in an
  `HttpOnly`, `Secure`, `SameSite=Lax` cookie named `heka_session`. Signing out deletes the row.
- **Moderators are configured by GitHub login** (`MODERATORS`, comma-separated) and mirrored into
  `users.is_moderator` at sign-in. Every moderator action writes a `mod_log` row, shown publicly
  at `/moderation`.
- **No email at launch.** Nothing needs it: no password resets, no notifications.

## Consequences

- Until phase 3 there is no sign-in: "Sign in" explains that membership is by invitation and
  sign-in opens soon.
- A response to a request carrying the session cookie is `private, no-store`; anonymous pages are
  cacheable by a shared cache. The switch is implemented now (`src/lib/http.ts`).
- GitHub is a dependency for signing in, not for reading.
